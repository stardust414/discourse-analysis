## 2. 文体和基本用语

- 界面使用简体中文，表达简短、自然、适合神学院用户；准确性优先于字面对齐。
- 操作按钮尽量用简短动词：保存、打开、导出、取消、删除、编辑、完成。
- 对于长文案，不为了缩短而省略取消后果、数据替换、覆盖编辑、撤销能力或安全限制。
- 中文完整句通常用句号；按钮、标题、简短悬停说明一般不加句号。原英文感叹号通常改成平实提示。
- 使用中文逗号、句号、冒号、引号与括号；代码、版本名、快捷键、缩写和实际符号可以保留半角字符。
- 专业成对名称用“—”连接，例如“行动—目的”；这是显示文本，不是修改原英文或内部 ID 的连字符。
- 文件扩展名、版本代码、数量、节号、项目代码和 URL 原样保留，不加会破坏复制或识别的空格。

普通操作词建议：

| 英文 | 推荐中文 | 使用边界 |
| --- | --- | --- |
| Save / Save As | 保存／另存为 | 不把导出图片和保存项目混称一种操作 |
| Open / Load / Import | 打开／载入／导入 | 依软件原操作区分，避免全部译作“导入” |
| Export / Download | 导出／下载 | 保留实际动作区别 |
| Add / Replace | 追加／替换 | 当前载入对话框中的 Add 是加入已有文档，不是新建文档 |
| Cancel / Discard / Dismiss | 取消／放弃更改／忽略 | 不混淆是否丢弃当前内容；具体见上下文 |
| Comments / Reply | 评论／回复 | 不把评论改称主旨摘要或用户正文 |
| Undo / Redo | 撤销／重做 | 保留全部原快捷键和可恢复行为 |
| Light Mode / Dark Mode | 浅色模式／深色模式 | 按钮表示要切换到的模式，不能误写成当前模式 |
| Cloud Sync / cloud session | 云同步／云端协作 | 项目代码和实际连接状态原样保留 |
| Project ID / project code | 项目代码 | 此处是界面叫法，绝不重命名存储字段 |

## 3. A–F 分类与审批规则

| 类别 | 范围 | 处理 |
| --- | --- | --- |
| A | 普通界面词汇 | 没有专业语义依赖者可推荐定稿 |
| B | 操作、状态、错误、确认 | 普通句可推荐定稿；含专业词者随术语待审 |
| C | 圣经研究、篇章分析、括号分析术语 | 仅建议，不自动定稿 |
| D | Logical Relationships／命题关系 | 逐项、逐 profile 审核，保留原英文名称和定义 |
| E | notation profile、主次、符号和自定义标签相关专业用语 | 仅建议，不自动定稿 |
| F | 帮助、较长说明、输入示例、无障碍操作说明 | 含专业内容时仍待审；长度不会降低审核要求 |

一条文字可能同时属于操作提示和专业内容。清单按主要用途分组，另独立记录“普通／专业相关”的风险状态；不能因归入 B 或 F 就直接批准专业译名。

## 4. 专业名称与双语显示

1. 关系全称原则上显示“中文名称 + English”，例如候选“理由 Ground”“推论 Inference”。这些示例仍需你审核。
2. 图内关系缩写和符号不汉化，不增加或删除星号，不替换 `/`、`//`、`∴`、`?` 等实际记号。
3. 五套 profile 的正式名称 Josiah、BibleArc、Gurtner、Beale、Schreiner 原样保留。当前 profile 的英文名称、缩写、星号位置、关系列表和颜色优先于默认常量。
4. 同一 ID 的不同英文叫法单列：Action-Manner／Way-End、Action-Purpose／Means-End、Concessive／Adversative 等不能为了中文化强行同名。
5. 即使两个定义接近，也不合并 Idea-Explanation、General-Specific、Fact-Interpretation、Bilateral、Double Ground 或旧 `cause-effect` 键。
6. 保留软件原有显示别名规则。显示为另一个体系的名称，不意味着已把文件中的原 ID 改成该名称，也不是术语学上的同义断言。
7. 专业短菜单可以使用你审核后的简称；英文完整名称应在首次出现、帮助或悬停中可查。关系选择器和指南优先保留完整双语。
8. 如果某条术语未获批准，后续不能自行把本轮建议变成正式中文；可保留原英文，并在后续报告中列明未决项。
9. 软件定义、定义的中文建议、白话解释和推荐理由要分开。白话解释不能冒充软件原文，软件原文也不自动等于各学者的完整学术定义。

## 5. 经文、用户内容和稳定值

下列内容不翻译、不统一、不自动改写：

- 经文正文，包括现有中文、希腊文、希伯来文和第二栏文字。
- 用户写的评论、回复、主旨摘要、姓名、项目标题和自定义关系名称／标签。
- 已保存的项目字段、内部 relationship ID、profile ID、云端名称键、版本代码、文件扩展名、导出嵌入标记和协议字段。
- 各 profile 原有缩写、颜色、主次和标签交换结果。
- 内部空行标记 `(empty)`，以及需要保留以维护现有数据语义的默认值。

`Imported text`、`Imported bracket`、`Anonymous`、`Custom`、`added verses` 有些会进入数据。表中的中文只在能明确区分显示文字和实际数据的地方使用，不批量迁移已有值，也不根据文字相同就替换用户内容。

译本选择只翻译名称说明，不改变所加载的数据。书卷输入示例继续保留 John、Romans、Phil 等现有可解析写法；本阶段没有新增中文书卷识别。软件品牌 Discourse Analysis、作者姓名、版权、来源和 attribution 保留。

## 6. 动态句子、数量和语序

- 每个翻译单元尽量是一条完整消息，使用具名变量；不沿用英文的词片段拼接方式。
- 中文数量不随英文单复数增加 `s`；注意“行”“节”“命题”“括号”各有实际含义，不能一律译成“条”。
- 动态值是数据，原样填入：人名、经文范围、项目代码、关系名、URL、错误详情不得当成翻译键再处理。
- 当前提取表为便于阅读把表达式简化为 `{count}`、`{name}` 等，精确英文和原表达式保存在证据清单。实施时逐项映射，不依靠这些可读变量名猜测代码。
- 原生确认框里有关“取消会生成新代码”、替换平行栏“包括所有编辑”等后果必须保留。
- 同一提示中支持的关系名称列表应按当前 profile 逐项生成，中文列表有独立连接方式，不硬拼英文 `or`。
- 导入成功旧文案与当前编辑模式存在不一致时，记录问题，不能在译文里无说明地改掉操作方式。

## 7. 所有显示渠道遵循同一规范

按钮、菜单、确认框、状态、错误、title、placeholder、ARIA、模板、CSS 拖放提示、屏幕阅读器信息都适用本规范。用户看不到的开发诊断日志不要求翻译；若错误详情会进入界面，外层提示应中文化并保留技术详情。

日期的显示格式可随界面语言变化，存储时间保持原值。快捷键显示遵循实际支持的 Ctrl／Cmd／Enter／Tab 等，不擅自改键位。界面语言不得影响希伯来文从右向左的经文方向。

Electron 自动菜单和系统原生按钮不在仓库英文字符串清单内，后续仍需实机验证。当前没有安装依赖或启动桌面应用，不能把源码提取结果当作完整运行验证。
