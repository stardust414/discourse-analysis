### 软件怎样组成

这是一套原生 HTML、CSS、JavaScript 界面，没有 React、Vue，也没有前端编译步骤。桌面版使用 Electron，即把这套网页界面装进桌面窗口的运行环境。

| 位置 | 对软件的作用 |
| --- | --- |
| `index.html`、`styles.css` | 页面结构、静态按钮和说明、样式、评论模板 |
| `app.js` | 启动、连接按钮与操作、经文载入和导入等提示 |
| `js/utils/ui*.js` | 菜单、关系选择器、对话框、评论、欢迎和设置 |
| `js/utils/render-*.js` | 经文、括号、箭头、评论和屏幕阅读器提示的生成 |
| `js/utils/constants.js` | 关系名称、分类、定义、关键词、固定标识符和缩写 |
| `js/services/profiles.js`、`notation-ui.js` | 五套 notation profile、搜索、编辑和分享 |
| `js/services/persistence.js`、`export-service.js` | 保存、恢复、最近项目，以及 JSON／PNG／PDF |
| `js/services/bible-service.js`、`cloud-sync.js` | 经文获取、云同步以及错误信息 |
| `js/utils/block-diagram.js`、`main-point-summary.js` | 方块图和主旨摘要界面 |
| `main.js`、`preload.js` | 桌面窗口、文件打开、主程序与页面之间的受控通信 |
| `functions/index.js` | 网页版经文 API 代理，不是本地桌面界面 |

应用以按顺序载入的普通脚本协作，主要通过 `DA_*` 名称访问其他组件。推荐延续这种结构，避免为了语言功能重做整个应用。

打包工具是 electron-builder。锁定依赖中的 Electron 为 28.3.3，electron-builder 为 24.13.3。正式 Mac 命令是 `npm run build:mac`，已有 `--mac --arm64` 参数，输出目录为 `dist/`，目标为 ZIP。普通 `npm run build` 会同时构建 Mac 和 Windows，最后交付 Mac 时不需要额外构建 Windows。

当前机器是 arm64，已有 Node v26.12.0、npm 11.20.0 和 Apple 命令行开发工具。这里只确认环境存在，尚未验证整条桌面构建链。

### 当前没有正式国际化机制

未发现语言字典、翻译函数、语言设置或语言切换事件。HTML 固定为 `lang="en"`，动态文字主要直接写在代码里。现有中文经文选项只是经文译本，不能视为中文界面。

### 推荐的国际化方案

采用**无新增运行依赖的小型字典层**：把界面文字集中保存，再按固定键读取，例如 `DA_I18N.t('passage.loaded')`。不引入框架，不更换打包工具。

建议结构：

```text
js/i18n/
  i18n.js          语言选择、回退、变量、统一文字更新
  en.js            完整英文基准
  zh-CN.js         已经审核的简体中文
  relationships.js 只供显示和搜索使用的专业关系名称适配
```

具体规则：

1. **English 是完整基准。** 中文缺项回退英文；两种语言都缺少键时，开发检查明确报出问题，运行时仍返回安全文字而非崩溃或 `undefined`。
2. **静态 HTML 使用统一标记。** 如 `data-i18n`，并对 title、placeholder、ARIA、data-placeholder 建立统一属性翻译规则。只修改指定文字节点，保留 SVG 图标、键位和按钮内部结构；不对整页进行英文搜索替换。评论模板克隆后也要应用翻译。
3. **动态文字统一调用翻译函数。** 完整句子带变量，按各语言分别安排数量、顺序、复数；不把英文碎片简单拼接成中文。不将用户输入作为翻译键，不把变量当成 HTML 执行。
4. **三种选择：跟随系统／English／简体中文。** 推荐首次使用“跟随系统”，按支持的语言匹配，其他语言回退英文。以独立本机设置（建议键 `biblebracket_language`）保存；不加入项目 JSON、云文档或撤销记录。本机存储不可用时仍可在当前会话选择语言。
5. **切换尽量即时生效。** 发出统一的语言变化通知，更新标记、可见菜单、关系指南、无障碍文字和动态按钮。保留经文、评论草稿、摘要、输入值、光标和选区，避免重新载入整页。系统语言改变只在“跟随系统”时影响当前语言。
6. **专业名称有独立显示层。** 内置关系按审核结果显示“中文名称 + 英文原名”；先遵循当前 profile 原有映射，再选择对应译名。保留 Gurtner 的 Way-End、Means-End、Adversative 等区别，保留各体系的缩写、星号、颜色、顺序和内部键。
7. **自定义名称优先原样显示。** 不直接改变现有 `getName()` 的原始数据语义，也不把翻译后的文字填回 profile 编辑输入框，以免一次编辑就把中文保存成用户自定义名称。不能明确识别为内置默认项的名称，不自动翻译。
8. **搜索同时支持中文与原有英文。** 给显示层增加中文名称／关键词索引，保留英文、缩写及其他体系的叫法。当前搜索标准化只接受英文字母和数字，实测“理由”会被清成空项，需要一处小范围适配，并测试中文输入法。
9. **错误在显示边界翻译。** 对已知内部错误用稳定错误代码映射界面文字；技术详情保留供排查。不会通过翻译第三方任意 `err.message`、或匹配英文错误句子来控制程序行为。
10. **补齐特殊渠道。** CSS 的 `Drop to import` 改成来自翻译属性的显示文字；日期遵循界面语言。原生确认按钮和 macOS 默认菜单须在 Electron 实机验证，因为系统按钮不一定服从应用内语言；必要时复用现有模态框和受控主程序通信，保持确认、取消和快捷键行为。

国际化脚本会在启动显示和欢迎框之前载入，避免首次启动先出现英文。新命名空间需同步补进现有代码检查的全局声明和类型声明。现有打包清单包含 `js/**`，可自然包含语言文件。

**不预计需要大量修改核心逻辑。** 会触及多个服务文件中的提示调用，以及关系搜索、错误传递、动态刷新等边界；括号算法、节号切分、dominance 规则、经文解析、稳定 ID 和文件迁移算法不需要为汉化重写。

## 3. 有没有风险或需要注意的问题

| 风险 | 意义与处理方向 |
| --- | --- |
| 界面英文与数据英文混在一起 | `(empty)` 被用作内部空行标记；`Imported text`、`Anonymous`、`Custom` 可能进入项目或 profile。只能翻译显示，不能直接替换底层值或用户内容。 |
| profile 名称与编辑内容混用 | 直接翻译 `getName()` 可能让中文混入自定义配置。使用独立显示层，保留五套体系和外来类型回退。 |
| 关系搜索目前过滤中文 | 仅翻译菜单后中文搜索会失效。补 Unicode 搜索与中文输入法检查，英文匹配能力也要保留。 |
| 英文消息已经离开界面层 | 服务和编辑逻辑中有英文错误、追加警告；撤销／重做使用英文操作名称。统一在展示时映射，避免让语言影响判断。 |
| 即时切换可能丢失正在输入的内容 | 语言切换不能粗暴重建所有可编辑区域。重点检查评论、摘要、经文和 profile 草稿。 |
| 中文及双语关系名更长 | 侧栏固定宽度、菜单、指南表格和弹窗需要后续视觉检查；调整必要布局，不改变分析结构。 |
| 希伯来文方向 | 界面语言不能覆盖经文独立的 RTL（从右向左）方向；也不能改动希腊文、平行栏和字体。 |
| 导出包含界面显示文字 | PNG／PDF 的可见标签可以随界面变化，但嵌入的项目数据必须保留原字段和原内容，JSON 也不写入界面语言。 |
| 原生菜单与确认按钮 | 需要分别验证应用控制的文字与系统控制的按钮；本阶段未声称它们已具备中英文切换能力。 |
| 当前浏览器测试很多依赖英文文字 | 保留原有英文测试，并明确指定英文语言；另加中文测试。不得删除断言来掩盖失败。 |
| 外部网络与云端 | Firebase SDK、Google Fonts、统计脚本仍来自网络；README 的“无 CDN”不能理解成完全离线。浏览器测试主动阻断外部请求，无法证明真实云同步、外部 API 或分享端正常。 |
| 桌面构建链尚未验证 | Electron 较旧，Node 当前较新；实际安装和构建时再验证兼容性。保持锁文件，不借汉化顺便升级依赖或改变签名策略。 |
